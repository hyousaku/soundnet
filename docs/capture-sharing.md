# H3 設計案 — キャプチャデバイスの共有（1入力 → N宛先）

**状態: 未承認。この文書の承認をもって実装に入る。**

---

## 1. 何を実現するか

「PC1 の I/F の IN1-2 を PC2 と PC3 の両方へ」を可能にする。

現状、送信パイプラインは1ルート＝1スレッド＝1デバイスで、スレッドが ALSA
デバイスを排他所有する。同じ入力を2つ目のルートに使うと `snd_pcm_open` が
EBUSY で落ち、2本目のルートは永久に retrying になる。エラーは
「Device or resource busy」で、**先客が自分自身の別ルートであることは
どこにも書かれていない**。

### 受け入れ条件（HANDOFF より）

- 同一入力デバイスから2宛先へのルートが同時に鳴る
- 既存の1対1ルートの遅延・xrun が悪化しない（実機で前後比較）
- チャンネル窓（offset）がルート毎に独立して機能する

### スコープ外

**再生側の共有（ミキシング）はやらない。** 2つのルートを1つの出力デバイスへ
向けるには加算・クリップ処理・ゲイン管理が要り、それは別の大きさの仕事。
今回の変更で再生側の挙動は1バイトも変わらない。

## 2. 設計 — DeviceOwner

デバイス1台につき1つの「オーナー」スレッドを立て、そこから各ルートの roc
sender へファンアウトする。

```
                       ┌─────────────────────────────────────┐
  hw:CARD=UMC,DEV=0 ──►│ DeviceOwner  (1 thread, SCHED_FIFO) │
                       │                                     │
                       │  snd_pcm_wait ◄── 唯一のブロッキング点│
                       │  snd_pcm_readi                       │
                       │  alsa_to_f32                         │
                       │  fade.apply                          │
                       │        │                             │
                       │        ├─ window::extract(0..2) ─► roc sender ──► PC2
                       │        ├─ window::extract(0..2) ─► roc sender ──► PC3
                       │        └─ window::extract(4..6) ─► roc sender ──► PC4
                       └─────────────────────────────────────┘
```

### 1周回の流れ

```
snd_pcm_wait(100ms)            ← ブロッキング点。ここは今と1文字も変わらない
snd_pcm_readi                  ← 1ピリオド
alsa_to_f32                    ← デバイスの全チャンネル
fade.apply(device_floats)      ← デバイス単位。今は窓抽出後だが等価
for each subscriber:           ← ここが新しい
    window::extract(offset, channels)
    publish_level(sub.level)
    sender.write()             ← 非ブロッキング
```

### 不変条件との照合

これが設計の核心なので、5つを1つずつ潰す。

**(1) デバイスのクロックが唯一のクロック。ALSA と roc の間にバッファを置かない。**

置かない。オーナースレッドが読んだピリオドを、その場で全 sender に直接書く。
中間バッファもリングも増えない。`send.rs` のモジュールコメントが記録している
「リングを消した理由」——ALSA がサウンドカードに、roc が CPU タイマーに
ペースされる2クロック問題——は**そもそも発生しない**。スレッドは依然1本で、
クロックも依然1つだからである。N個の sender は同じ1つのクロックに乗る。

**(2) 1周回にちょうど1つのブロッキング点。**

守られる。`roc_sender_write` は `ROC_CLOCK_SOURCE_EXTERNAL` 設定下では
非ブロッキング（パケット化して `sendto` して即座に返る）。N回呼んでも
ブロッキング点は増えない。ブロッキング点は `snd_pcm_wait` のまま1つ。

ただしコストはゼロではない: 1周回あたり N 回の `sendto`。128 frames /
48 kHz = 2.7ms の周期に対して数マイクロ秒のオーダーなので N=3〜4 では
問題にならない見込みだが、**これは推定であって実測ではない**（§8 参照）。

**(3) RT 権限が取れなくても警告して動き続ける。**

変更なし。`rt::raise_thread_priority` の呼び出し位置がスレッド1本あたり
1回になるだけ。

**(4) 再生は start_threshold=buffer_size。**

再生側は触らない。

**(5) デバイスはカード ID で命名する。**

デバイスレジストリのキーは `alsa_name`（すでにカード ID 形式）。番号は
使わない。

### 副次的な利点

ルート N 本が1スレッドになるので、**スレッド数が減る**。ラズパイで1入力を
3宛先に配るとき、今なら3スレッドが同じデバイスを開こうとして2本が失敗する。
新設計では1スレッドで3宛先を賄う。CPU 的にはむしろ軽くなる。

## 3. 共有デバイス上のルートが一致していなければならない項目

デバイスは1度しか開けないので、開き方を決める項目は全ルートで一致が必要。

| 項目 | 共有可否 | 理由 |
|---|---|---|
| `rate` | **一致必須** | デバイスのハードウェアパラメータ |
| `frames_per_period` | **一致必須** | 同上。1周回に読む量が1つに決まる |
| `alsa_format` | **一致必須** | 同上 |
| `channels` / `channel_offset` | 独立可 | 窓抽出でルート毎に切り出す |
| `target_latency_ms` | 独立可 | 受信側のジッタバッファ設定 |
| `fec` | 独立可 | sender 毎の設定 |
| 宛先 | 独立可 | これが目的 |

不一致のルートを追加したときの挙動は **H4 と同じ形にする**: 起動を拒否し、
エラーメッセージに**先に走っているルートの id と、食い違っている項目**を
書く。「デバイスがビジー」で終わらせない。

```
capture hw:CARD=UMC,DEV=0 is already open at 48000Hz/128f/S24_LE3 for
route "studio-to-booth"; this route asks for 96000Hz/128f/S24_LE3.
Change one of them to match, or use a different input.
```

UI 側の追随（共有中のデバイスではドロップダウンをロックする等）は**この
コミットではやらない**。まずエラーが読めることを優先し、UI は別途。

## 4. チャンネル窓の広げ方 — ここが承認の要る判断点その1

デバイスは「窓の右端まで」開く（既存のコメント: 16ch I/F の ch5 を読むのに
16ch 開くのは USB 帯域の無駄）。共有すると、後から来たルートが今開いている
窓より右を要求しうる。

- **ケース A**: 既存が ch1-2 で開いている。新ルートが ch1-2 を要求 → 再オープン不要。
- **ケース B**: 既存が ch1-2 で開いている。新ルートが ch5-6 を要求 → **ch1-6 で開き直す必要がある**。

ケース B の選択肢:

| 案 | 挙動 | 評価 |
|---|---|---|
| **B1 拒否** | 新ルートを「既存ルートの窓に収まらない」というエラーで失敗させる | 既存の音は絶対に途切れない。しかし「ch5-6 に繋ぎたいなら既存ルートを一度消せ」というのは操作として不合理 |
| **B2 開き直す** | オーナーを止めて広い窓で開き直し、全 sender を繋ぎ直す。既存ルートに数十〜数百 ms の断が出る | 操作として自然。ただし**他人の音を止める** |
| **B3 常に最大で開く** | ポートの `max_channels` で常に開く | 断が起きない。しかし既存コメントが名指しで否定している「16ch 開いて1本運ぶ」を全ケースでやることになる |

**推奨は B2。** 理由:

- パッチを足すのは operator の意図的な操作であり、その瞬間に短い断が出ること
  は予期できる。無音のまま「なぜか繋がらない」より遥かに良い。
- B3 は USB 帯域とラズパイの CPU に恒常的なコストを課す。断が出るのは
  パッチ追加の瞬間だけなので、恒常コストと引き換えるのは割に合わない。
- B1 は「消して作り直せ」という手順を人間に押し付ける。それは結局 B2 を
  手でやっているのと同じで、断も同じだけ出る。

**ただし B2 は「他人の音を止める」ので、これは私が勝手に決めるべきではない。**
ライブ運用で ch5-6 のパッチを足した瞬間に ch1-2 が途切れるのが許容できるか
は運用の問題。許容できないなら B1（拒否 + 明確なエラー）にする。

B2 を採る場合でも、断は**ログと UI に必ず出す**。無言で音が途切れるのが
最悪なので、「route X を追加したためデバイスを ch1-6 で開き直した」と言う。

## 5. ライフサイクル

```rust
// EngineState
pub capture_owners: DashMap<String /* alsa_name */, Arc<DeviceOwner>>,
```

- ルート開始時: `alsa_name` でオーナーを引く。無ければ作る（スレッド起動）。
  あればスペックの一致を検査し、subscriber を追加する。
- ルート停止時: subscriber を外す。最後の1つが外れたらオーナーを止めて
  レジストリから消す。
- subscriber の管理はオーナー内部の `Mutex<Vec<Subscriber>>`。オーディオ
  スレッドは1周回に1回だけ `try_lock` して読む。**取れなければ前回の
  リストのままその周回を回す**（後述）。

### ロック順序 — 承認の要る判断点その2ではないが、事故りやすいので明記

H1 で入れたルート単位ミューテックスとの順序は **route lock → owner registry**
の一方向に固定する。逆順は絶対に作らない。デッドロックの典型パターンで、
テストで捕まえにくい。

### オーディオスレッドが subscriber リストを読む方法

`Mutex<Vec<Subscriber>>` を SCHED_FIFO スレッドから `lock()` するのは
優先度逆転のリスクがある（低優先度の制御スレッドがロックを持ったまま
プリエンプトされると、RT スレッドが待たされる）。

対策: オーディオスレッド側は `try_lock` のみ。取れなかった周回は**自分が
持っているスナップショットのまま送る**。subscriber の追加・削除が1周回
（数ミリ秒）遅れるだけで、音には何の影響もない。ロックを持つ側（制御
スレッド）は Vec を差し替えるだけなので保持時間はナノ秒オーダー。

代替として `arc-swap` や二重バッファも考えられるが、依存を増やす価値がある
ほどの差ではない。`try_lock` + スナップショットで十分。

## 6. 障害の分離 — 1本の失敗が全員を殺さない

現状は sender エラーが `consecutive_errors` を上げ、`MAX_CONSECUTIVE_ERRORS`
でパイプラインごと死ぬ。共有下でこれをやると、**1つの宛先が死んだだけで
他の宛先の音も止まる**。

- `consecutive_errors` を **subscriber 単位**に持つ。
- ある subscriber が上限に達したら、その subscriber だけをファンアウトから
  外し、そのルートを failed としてマークする。オーナーと他の subscriber は
  走り続ける。
- デバイス側のエラー（xrun、read 失敗）は今まで通りデバイス単位。これは
  全 subscriber に等しく影響するので当然。

## 7. 統計と UI

デバイス由来の値は共有され、ルート由来の値は独立する。

| 値 | 帰属 |
|---|---|
| `capture_xruns` | デバイス。共有ルートは同じ数を報告する |
| `capture_buffer_ms` | デバイス |
| `capture_format` | デバイス |
| stalled (capture) | デバイス |
| `capture_level_db` | **ルート**。窓が違えばレベルも違う |

xrun 数が複数ルートで同じ数字になるのは正しい——同じデバイスの同じ
オーバーランなので。ただし「合計しているのでは」と誤読されうるので、
UI のツールチップに一言足す（「この入力デバイスを共有する全ルートで共通」）。

## 8. 採らなかった案

**リングバッファでファンアウトする** — オーナーが読んでリングに書き、
sender 毎のスレッドが読む。`send.rs` のモジュールコメントが記録している
通り、これは(a)3ピリオド分の純粋な遅延を足し、(b)ALSA と roc に別々の
ペースを与えて必ずドリフトする。**今回この案を採る理由が1つも無い**:
`roc_sender_write` が非ブロッキングである以上、書き込みを別スレッドに
逃がす必要がそもそも無い。

**デバイス毎にプロセスを分ける** — 排他問題は解けるが、プロセス間で
オーディオを渡す手段が必要になり、それは結局リングバッファである。

**ALSA の `dsnoop` プラグインを使う** — カーネル側で共有を解決できるが、
`hw:` から `dsnoop:` に変わると period/buffer の制御が効かなくなる。
このプロジェクトの低遅延はまさにそこを直接叩くことで成立しているので、
根幹と引き換えになる。

## 9. 実装の刻み方（1コミット = 1行）

1. `DeviceOwner` と subscriber の骨組みを入れ、**subscriber が常に1個**の
   状態で既存の1対1ルートを通す。振る舞いは一切変わらないはずで、
   ここで遅延と xrun を実機で前後比較する（受け入れ条件の2つ目）。
2. subscriber を複数にできるようにする。スペック一致検査と、不一致時の
   H4 形式のエラー。
3. 窓の拡張（§4 で承認された案）。
4. 障害の分離（subscriber 単位の `consecutive_errors`）。
5. 統計の帰属整理と UI のツールチップ。

1 で止めても既存機能は壊れず、2 で受け入れ条件の1つ目が満たされる。

## 10. リスクと、まだ確かめていないこと

- **N回の `sendto` が2.7ms の周期に収まるか** — 推定であって実測ではない。
  ラズパイ4で N=3、128 frames/48 kHz が現実的な上限テストになる。
  ステップ1で1対1の前後比較を取ると書いたのは、この余裕を測るため。
- **`roc_sender_write` が本当に常に非ブロッキングか** — libroc の
  `ROC_CLOCK_SOURCE_EXTERNAL` はそう振る舞うはずだが、送信ソケットの
  バッファが埋まったときの挙動は未確認。埋まる状況（NIC 飽和）は N 倍で
  起きやすくなる。ステップ1で確認する。
- **私はサウンドカードを持っていない。** この設計のどの部分も、実機で
  動かすのは人間の仕事になる。合成テストで押さえられるのは窓抽出、
  スペック一致検査、subscriber の追加削除とライフサイクルまで。

## 11. 承認が要る点

1. **§4 の窓拡張。B2（開き直す＝既存ルートに短い断）を推奨するが、
   ライブ運用で許容できるか。** 許容できないなら B1（拒否）にする。
2. **§3 の一致必須項目。** rate / period / format を共有デバイス上で
   揃えさせる、という制約でよいか。（技術的にこれ以外の選択肢は無い。
   確認のみ。）
3. **§9 の刻み方でよいか。** 特にステップ1（振る舞いを変えずに構造だけ
   入れて実機で前後比較）を挟むことに同意頂けるか。ここを飛ばすと、
   後で遅延が悪化したときに原因が構造なのかファンアウトなのか切り分け
   られなくなる。
